# 架构：从一句话到一个完整的全栈应用

北极星目标：用户说一句 *"给我做一个微信点餐小程序"*，就能得到一个可运行、接近商用水准的全栈应用。诚实且可达的版本是：harness 完成约 90% 的工程工作，人类只在少数无法——或不应——自动化的边界上留在回路中。外部集成（微信登录、支付）在一条明确标注的边界后面用 mock 实现，由人类验证。本文档描述的是从 castle 的现状——小型、单语言、自包含、以单元级验收为准的库——走向那个目标的架构。

## 为什么难：叶子节点并不独立

castle 目前假设分解后的叶子节点只触碰**互不相交的文件**，在隔离的 git worktree 中构建，并能够干净合并。这对字符串库成立，但对全栈代码不成立，原因有三：

1. **共享产物**——DB schema、API 契约、共享类型、auth——会被许多任务触碰。
2. **共享代码协同演化**：构建 `checkout` 常常会迫使 `order` 模型发生变更，而 `cart` 也依赖这个模型。
3. **真实的依赖图是在实现过程中才被发现的**，计划阶段无法完全预知。

依赖 DAG 是正确的*表示*——人类分解时也会带着依赖。差距在于：castle 目前把任务**冻结**在互不相交的文件孤岛里，而真实开发会自由地编辑共享代码、不断地重新规划。弥合这个差距，正是本文档的内容。

## 设计

### 1. 契约优先的分解（Contract-first decomposition）

分解在**最早的一批 wave** 中就产出一组 *契约（contract）* 任务：DB schema、共享类型、API 接口。其他一切都依赖它们。尽早冻结契约是让并行开发保持干净的最大杠杆——它把共享文件中的变动降到最低。契约并非不可变，但修改契约是一个深思熟虑、协调一致的行为（见下文），绝不是随手一改。

### 2. 共享编辑协议——一个频谱

当 dev agent 需要修改一个它并不拥有的文件（共享/契约文件）时，harness 在**工具层**拦截这次写入（与权限系统所用的同一个接缝），并将其路由到一个协调协议中，而不是直接编辑。每一次共享变更都落在该频谱的某个位置：

```
small   → 自动合并到 integration branch
medium  → 合并 + 重新运行每个依赖任务的验收测试
break   → 合并 + 为现在失败的任务派生 fix-agent
large   → 重新规划受影响的子树
```

**机械层（git）。** 一条全局的 **integration branch**（基于 trunk）。请求方 dev agent 阻塞；一个专门的 editor agent 在自己的分支上完成共享变更，再合并到 integration branch——串行化，一次只处理一个共享写入。dev agent 从 integration branch 分叉，并 rebase 到它之上。（只有一条全局分支，而不是每个 wave 一条：契约是全局的；按 wave 分叉只会增加复杂度，却解决不了跨 wave 的契约变更。）

**语义层（git 合并覆盖不到的那一半）。** 契约变更会使按旧契约构建的依赖方*代码*失效——`cart` 是按旧的 `order` 模型写的，现在调用的是一个过时的签名。因此，共享变更落地后，harness 会计算出依赖方（导入被变更文件的任务），重新运行它们的验收测试，并为失败的那些派生 **fix-agent**（复用现有的验收修复循环）。如果某个依赖方无法在本地修复，就升级为重新规划。

机械层 + 语义层合在一起，才等同于人类所说的"编辑共享文件，然后修复它碰过的所有东西"。朴素的版本（阻塞、专门 agent、合并回去）只是机械的那一半。

### 3. 构建中途的重新规划（Mid-build replanning）

计划在批准之后并不会被冻结。当某个任务报告"我需要计划里没有的东西"，或某个共享变更大到无法吸收时，harness 会暂停，重新规划受影响的子树（限定在该区域内的分解），并抛出一个人类可以审阅的 **replan checkpoint**——与 approve-plan checkpoint 相同的 HIL 机制。"小变更 → 涟漪式重测"和"大变更 → 重新规划"是一个频谱的两端，而不是两套独立的系统。

### 4. 集成测试环境

单元验收（每个任务跑 `bun test <file>`）是必要的但不充分——真正的 bug 藏在集成里：状态机、并发（两个用户抢最后一件商品）、DB↔API↔client 的接缝。这需要一个 **test-environment harness**：拉起 DB 和服务器、灌入种子数据、打端点、再拆除。它是一个子系统，而不是更多的测试文件。集成测试作为整个构建的关卡，位于按任务划分的单元关卡之上。

### 5. 安全与性能审查，以及人类签收队列

两个新的对抗式审查阶段，建立在现有的**上下文隔离审计器（context-isolated auditor）**模式之上（就是那个已经能防止 agent 给自己的作业打分的机制）：

- **安全审查（Security review）**——专攻低门槛、高严重性缺陷类别的 agent：authz / IDOR、注入、密钥处理、支付边界与回调验证。多个审查者，多数表决。
- **性能审查（Performance review）**——N+1 查询、缺失的索引、明显热点路径。

一个**风险分类器（risk classifier）**对发现进行路由：可自动修复 → fix-agent；需要人类判断 → **人类签收队列（human sign-off queue）**，推迟并呈现给用户。我们无法证明 bug 不存在；诚实的标的是把低门槛、高严重性缺陷的概率压到**低于典型开发者能达到的水平**——并通过一个注入并评分这些缺陷类别的 eval，让这一点*可度量*。这个度量本身就是意义所在（这就是"用真实任务作为反馈信号"）。

### 6. 多模型路由

DeepSeek 是文本/代码模型，没有视觉能力。UI/设计任务路由到多模态模型，负责视觉生成与设计审查；代码任务留在 DeepSeek 上。harness 对每个任务是模型无关的——模型路由本身就是 harness 的一项能力，而不是权宜之计。

### 7. 外部边界

真实账号、凭据、支付商户入驻、部署、ICP 备案、商店审核，都不在自主工作的范围内。外部集成（微信登录、支付）在**一条明确的边界后面用 mock 实现**。这些 mock 边界——恰恰是真实 bug 和安全漏洞藏身之处——被标注为**必须由人类验证（human-must-verify）**；构建通过绝不意味着这些部分已达到生产可用。

## 人类留在哪里（这是设计使然，而非能力所限）

- 设计签收（产品是什么），
- 计划批准（DAG，在任何代码之前），
- 重新规划审查（计划在其执行过程中发生变化时），
- 安全签收（风险队列），
- 一切真实世界的事物：账号、凭据、部署、支付入驻、商店审核，以及商业验收（总要有人对钱负责）。

## 这不是什么

- 不是"一句话、零人类、保证商用级"。当前没有任何系统能做到，而且其中一部分（账号、备案、商店审核、为钱负责）本质上是人类的。
- 不是正确性证明。它降低缺陷概率；它不消除缺陷。

## 能力分层

| 层级 | 目标 | 状态 |
|------|------|------|
| **T0** | 小型单语言自包含库，单元验收 | ✅ 已验证 |
| **T1** | 小型多文件单语言应用，端到端 | 接近（契约优先 + 集成测试） |
| **T2** | 小型全栈应用（前端 + 后端 + DB），共享契约，集成 + 安全/性能审查，人类守在边界 | **本文档的目标** |
| **T3** | 商用微信小程序，已部署、通过商店审核 | 登月目标；部分无法自动化 |

## 它复用了什么

这是对已有成果的演进，而不是重写：

- 上下文隔离的对抗式**审计器** → 安全与性能审查，
- 验收**修复循环** → 对失败依赖方的涟漪式修复，
- **HIL checkpoints**（clarify、approve-plan）→ replan checkpoint，
- **git worktrees** → integration branch + 共享编辑协议，
- **工具层拦截** → 共享文件守卫（以及权限系统），
- 单一的 **AgentEvent / BuildEvent** 流 → replan / ripple / security 事件。

这个模式本来就是对的。全栈这一步的关键，是让共享代码成为一等公民：契约优先、带语义涟漪的协调式共享编辑协议、构建中途重新规划，以及瞄准那些真正要紧的 bug 的审查阶段。
